# 技術目錄（tech-catalog.md）寫法

使用者需求：「整理出目前專案所用的技術，並寫成目錄，再來需要說明每項技術的要點」。接手的人常卡在「這個套件 / 服務是什麼、在這裡怎麼用、有哪些地方要注意」。handover.md 是照模組寫的，tech-catalog.md 則是照技術寫：同一個技術散在好幾個模組裡，這份文件把它收在一處。

## 1. 盤點：只列真的有在用的

依序收集，每一項都要有證據（import、設定檔、建置腳本、SQL 表名）：

1. facts 的相依清單（`pyproject.toml`、`requirements*.txt`、`package.json`、notebook 的 `%pip install`）。
2. 用 `grep -rhoE "^(from|import) [a-zA-Z_]+" --include=*.py` 等方式，找出實際被 import 的套件。notebook 則從 cell 原始碼抓。
3. 基礎設施與外部服務：Dockerfile、CI（buildspec、GitHub Actions）、IaC、settings / 環境變數**名稱**、HTTP client 呼叫的 host、SQL 用到的 schema / table。
4. 演算法與方法（BM25、Node2Vec、YOLO、NMS、餘弦相似度…）也算技術，要列進目錄。

相依清單裡有、但程式沒有 import 的套件，放在最後的「宣告了但沒用到」表，不展開。

## 2. 分級

| 等級 | 定義 | 寫法 |
|---|---|---|
| 核心 | 不懂它就看不懂主流程或改不動（主框架、模型、主要資料庫、核心演算法） | 完整一節（見第 4 點） |
| 常用 | 會碰到、但照著現有寫法就能改（設定載入、HTTP client、log） | 精簡一節：是什麼＋在哪用＋1–3 個要點 |
| 周邊 | 工具或輔助（formatter、測試工具、型別套件） | 只在目錄表出現一列 |

## 3. 文件結構

```markdown
# <專案名> 技術目錄

> 範圍：<repo / 分支 / commit>｜盤點日期：YYYY-MM-DD｜依據：相依檔 + 實際 import + 建置設定

## 目錄

| 分類 | 技術 | 版本 | 等級 | 在本專案做什麼 |
|---|---|---|---|---|
| 語言與執行環境 | [Python](#python) | 3.11（Dockerfile） | 核心 | 服務與訓練都用它寫 |
| Web / API | [FastAPI](#fastapi) | 0.110 | 核心 | 對外 REST API |
| … | | | | |

## 語言與執行環境
### Python
…

## 宣告了但沒用到
| 套件 | 宣告位置 | 備註 |
```

**分類順序**（沒有的分類就跳過）：語言與執行環境 → Web / API 框架 → 資料處理 → 機器學習與演算法 → 資料庫與儲存 → 外部服務與 API → MLOps / 模型管理 → 建置、部署與雲端 → 設定、log 與監控 → 開發與測試工具。

- 目錄表的技術名稱要連到下方的小節（GitHub 風格錨點：小寫、空白換成 `-`，中文保留）。
- 版本以 lock 檔或建置設定為準；沒有鎖版本就寫「未鎖版本」，這本身就是一個要點。

## 4. 每項核心技術的小節

```markdown
### Node2Vec（PyTorch Geometric）

**一句話**：在圖上隨機走路，把走過的節點當成句子，用 skip-gram 學出每個節點的向量。

**在本專案**：`training/graph_embedding.py:40-120`（`train_node2vec()`）；推薦服務只讀它產出的向量（`service/similarity.py`）。

**關鍵設定**：`embedding_dim` 128、`walk_length` 20、`p` 1、`q` 1.5（`configs/train.yaml`）。

**要點**
1. p / q 控制走法：q > 1 傾向在附近繞（BFS），學到「同一群」的相似。
2. PyG 原生版的遊走不看邊權重；需要加權時要自己覆寫取樣。
3. 向量只對圖上有的節點存在：新書在下一次重訓前查不到（冷啟動）。

**注意**：嵌入維度改了，服務端讀向量的程式也要一起改。
**延伸閱讀**：Grover & Leskovec 2016〈node2vec〉；PyG `torch_geometric.nn.Node2Vec` 文件。
```

寫作原則：

- **要點寫「在本專案要懂的」**，不是教科書摘要：每個要點盡量連到本專案的用法、設定值或踩過的坑。3–6 點。
- 演算法類技術的公式與應用場景已經在 handover.md 的核心流程寫過，這裡只寫一句原理＋要點，並連到 handover.md 對應小節，不要重寫。
- 外部服務寫清楚：誰提供（自己 / 別組 / 第三方）、怎麼認證（只寫環境變數**名稱**）、失敗時本專案怎麼處理。
- 版本、參數、檔案位置都附出處（`file:line`、Cell N、設定檔名）；推測標「（推測）」。
- 簡報者就是作者時，「注意」寫成中性的事實或下一步（見 teaching-style.md）。

## 5. 和其他產出的關係

- handover.md 的「技術棧」一章改成摘要表（分類｜技術｜一句話），開頭寫「每項技術的要點見 tech-catalog.md」。
- 簡報只放一頁「用到哪些技術？」（`table`：分類｜技術｜一句話要點），放在「一張圖看懂」之後；只列核心與常用，最多 12 列，超過就拆兩頁或只列核心。
- 多 repo：一份 tech-catalog.md，目錄表多一欄「repo」；同一技術在不同 repo 用法不同時，在同一小節分段說明。

## 6. 數據科學家必備技術

目錄裡的演算法與方法（機器學習、檢索、評估、實驗設計等），挑出「數據科學家必須懂」的，在目錄表的等級欄加註「DS」，並在簡報做成英文解說章節。挑選與寫法見 `ds-essentials.md`。
