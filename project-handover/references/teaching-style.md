# 簡報風格：輕鬆導讀、演算法講細（預設）

這份風格來自使用者的實際回饋：「不要太生硬，架構簡單帶過，演算法說細節一點，其餘用活潑一點的方式呈現」，以及「不需要第一週任務」。完整、正式的資訊放 handover.md；簡報的任務是讓人**聽懂系統怎麼想事情**。

## 頁序骨架（約 25–35 頁）

| # | 頁面 | 頁型 | 寫法 |
|---|---|---|---|
| 1 | 封面 | `title` | 標題是一個問題（「一張發票照片，怎麼變成一筆帳？」「買過這本書的人，下一本要推什麼？」），副標放專案 / repo 名 |
| 2 | 今天的路線 | `agenda` | 每項一句口語說明 |
| 3 | 先看結果 | `two_column` | 左：你送進來的；右：你拿回去的（虛構 JSON 或範例） |
| 4 | 一張圖看懂 | `diagram` | 4–6 個節點的步驟圖＋一個 note 說「哪些是模型、哪些是規則、哪些是外部服務」。這是唯一的架構圖 |
| 5 | 用到哪些技術？ | `table` | 從 tech-catalog.md 取核心與常用技術，欄位：分類｜技術｜一句話要點，最多 12 列；講者備註指向 tech-catalog.md |
| 6 | （選用）模型 / 資料怎麼到線上 | `flow` | 4–6 步，30 秒講完 |
| 7+ | 先備知識 section | `section` + 2–3 頁 | 後面演算法需要的概念，用一張表或一個流程解釋，再用一個小情境驗證理解 |
| … | 每個演算法環節一個 section | 見下 | 這是簡報主體，通常占一半以上頁數 |
| 末-4 | Data Science Essentials | `section` + 總覽 `table` + 每項 1–2 頁 + References | 見 `ds-essentials.md`：英文解說、中文「在本專案」callout |
| 末-3 | 踩雷地圖 | `cards`（tag 高 / 中） | 每張卡一句口語標題（「檢查沒有生效」「門檻會被改掉」）＋一句說明 |
| 末-2 | 上線只要 N 步 | `flow` | 部署縮成一頁，⚠ 標出風險步驟 |
| 末 | Q & A | `closing` | 標題用預設「Q & A」，bullets 只放延伸閱讀（handover.md、tech-catalog.md）。**不要**放「接下來想一起做的事」「還沒有答案的問題」這類待辦或問題清單（使用者明確要求）；待確認事項留在 handover.md |

**不放**：目錄導覽、每項技術的細節（在 tech-catalog.md）、環境變數表、專案歷程 timeline、學習路徑、第一週任務、交接清單、各模組架構圖。它們都在 handover.md。

## 每個演算法環節的講法

1. **它在解決什麼問題**：一句話，最好是問句當 section 標題（「Step ①：這是發票還是收據？」）。
2. **為什麼這樣設計**：舊做法哪裡不夠（`two_column` 舊 vs 新），有實驗數據就放（「20 張收據有 3 張被誤判成發票」）。
3. **規則 / 公式本身**：決策用 `diagram`，公式或規則用 `table` 並加「白話」欄。
4. **應用場景**：一個具體的人 / 一筆資料走一遍；分支多時用表格並列（「四張照片，四種結局」）；參數類用「同一筆輸入、兩組參數」對照。
5. **容易忽略的細節**：`cards`（3 張以內），或發現的 bug 用 `code` 頁（標題「抓到一個 bug：…」），前一頁的 callout 留懸念（「為什麼？看下一頁」）。

## 圖上的文字要少

使用者回饋：「流程圖的文字都太多，很難解讀」。圖是用看的，不是用讀的：

- `flow`：每步一個短標籤（≤ 8 字）＋一句話（≤ 16 字），例：「信心過濾｜低於 conf 丟掉」。公式、參數名、函式名放備註。
- `diagram`：方塊 = 名稱 + 一個關鍵事實（≤ 2 短行）。應用場景的方塊只寫「這一步的結果」（「B990 太新 → 剔除」），不寫為什麼。
- 被拿掉的細節一律移到講者備註，不要直接刪。
- 產生器的 FIT WARNINGS 出現 `too long` 時，改寫文字，不要忽略。

## 簡報者就是作者時：別扯他後腿

使用者回饋：「我怎麼覺得簡報你在扯我後腿？」那份 code 幾乎全是使用者自己寫的，簡報卻寫成外部稽核：「抓到一個大問題」「白算了」「結果很看運氣」「原負責人知道嗎？」，等於讓他在台上自己打臉。

- 動筆前先比對 `git shortlog -sne` 與使用者身分（email / GitHub 帳號）。主要作者是使用者本人，或使用者是要上台介紹這個系統的人，簡報就要用**作者的視角**來寫。
- 問題寫成「設計取捨」或「下一步」，不要寫成「bug」：`code` 頁「抓到一個 bug」改成 `two_column`「現在 → 下一版」；「踩雷地圖」改成「下一步：還能更好的地方」（tag 用 優先 / 規劃）。
- 加一頁「這套系統做對的事」，把每個演算法環節的亮點收在一起。
- 措辭不要帶情緒或貶義（白算、很看運氣、形同虛設、偷偷），不要點名「原負責人」。
- 事實不變：問題本身、`file:line` 照樣留在講者備註與 handover.md，handover.md 可以直接寫「已知問題」。
- 使用者說問題修好了，就去讀新的 commit 驗證，再把簡報從「下一步」改成「新版做了什麼」。

接手交接、或使用者明確要做 code review / 稽核時，才用原本直白的「踩雷地圖」寫法。

## 語氣

- 標題：問句、口語、可以帶一點懸念；避免「XX 模組架構」「XX 流程說明」這類標題。
- 內文：「你送進來的 / 你拿回去的」「寧可不答，也不跑錯模型」這種說法；技術名詞保留原文，第一次出現時給白話。
- callout：一句結論或一個伏筆。
- 講者備註：口語、3–6 句；包含 `file:line`、為什麼這樣設計、可以問台下的問題（「如果發票號碼第 5 碼被讀成 O，該怎麼修？」）。
- 不用 emoji（預覽字型無法顯示）；可以用 ✓ ✗ ⚠ ① ② → 等符號。

## 主題色

預設 `"theme": {"primary": "#1F6F8B", "accent": "#F08A4B"}`（藍綠＋暖橘），比深藍活潑。使用者指定品牌色時照用。
